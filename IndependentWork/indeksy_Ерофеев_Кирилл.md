## Письмо 2. Индекс под запрос

### Задание 1. Ошибки, которые выполнялись дольше двух секунд.

```js
db.events.find({ level: "error", duration_ms: { $gt: 2000 } })
```

```js
db.events.createIndex({ level: 1, duration_ms: 1 })
```

- План: FETCH → IXSCAN level_1_duration_ms_1; ключей прочитано 87, документов прочитано 87, возвращено 87
- Наилучший индекс, попыток: 1

### Задание 2. Двадцать последних событий маршрута оплаты.

```js
db.events.find({ route: "/api/pay" }).sort({ ts: -1 }).limit(20)
```

```js
db.events.createIndex({ route: 1, ts: 1 })
```

- План: LIMIT → FETCH → IXSCAN route_1_ts_1; ключей прочитано 20, документов прочитано 20, возвращено 20
- Наилучший индекс, попыток: 1

### Задание 3. Ошибки сервиса поиска по порядку времени.

db.events.createIndex({ service: 1, level: 1, ts: 1 })

### Задание 4. Запрос А — все события маршрута входа. Запрос Б — те из них, что закончились ошибкой. Нужен один индекс, с которым оба запроса читают столько, сколько возвращают.

```js
// Запрос А
db.events.find({ route: "/api/login" })
// Запрос Б
db.events.find({ route: "/api/login", status: { $gte: 400 } })
```

```js
db.events.createIndex({ route: 1, status: 1 })
```

- Запрос А. План: FETCH → IXSCAN route_1_status_1; ключей прочитано 207, документов прочитано 207, возвращено 207
- Запрос Б. План: FETCH → IXSCAN route_1_status_1; ключей прочитано 68, документов прочитано 68, возвращено 68
- Наилучший индекс, попыток: 1

## Письмо 3. Вес индексов

- Прогноз: service_1 → user_id_1 → trace_1 → ts_1
- Измерение на 1 000 000 событий: service_1 — 5,0 МБ; user_id_1 — 7,4 МБ; ts_1 — 11,3 МБ; trace_1 — 15,0 МБ
- На своих местах: 2 из 4
- Вопрос 1: _id_, ts_1, trace_1, user_id_1_ts_1 — верно
- Вопрос 2: Вырастет примерно на 5 МБ — неверно
